# Decisiones — backend-builder

Registro de decisiones de implementación del backend. Estructura y reglas comunes en `docs/decisions/decisions.md`.

| Fecha | Agente | Feature | Decisión o pieza | Problema o necesidad | Decisión adoptada | Motivo | Cómo se verificó |
| ----- | ------ | ------- | ---------------- | -------------------- | ----------------- | ------ | ---------------- |
| 2026-10-03 | backend-builder | F1 | Estructura de capas del backend | Hay que cumplir Clean Architecture con dependencias hacia el interior (RNF-Q-01 a RNF-Q-04) | Paquete `backend/app` con `dominio` (elemento, dependencia, catálogo/grafo, errores, validación), `aplicacion` (casos de uso y puerto `RepositorioCatalogo`), `infraestructura` (repositorio en memoria, datos sintéticos) y `api` (esquemas, rutas, errores HTTP). El dominio no importa FastAPI ni persistencia | Permite verificar que cada regla de F1 vive en un único lugar y que el frontend pueda consumir la API sin duplicar lógica | `py_compile`/`compileall` sin errores; inspección de importaciones (el dominio solo importa de `app.dominio`); humo de endpoints con TestClient |
| 2026-10-03 | backend-builder | F1 | Representación propia del grafo | F1 necesita exponer la red sin bibliotecas de grafos (RNF-F1-03, AC-F1-15) | Clase `Catalogo` con mapa `id → elemento` y dos índices de adyacencia (`salida` y `entrada`) como conjuntos, actualizados en la misma operación de registro; listados ordenados por identificador ascendente | Cumple las invariantes de `graph-model.md` §3.3 (sin paralelas, sin reflexivas, adyacencias cubriendo todos los elementos, grafo vacío válido) y responde adyacencias en tiempo constante/lineal | Casos límite ejecutados: grafo vacío, elemento sin dependencias, duplicados, reflexivas, dirección de lista (`tipoRelacion: "habilita"`) |
| 2026-10-03 | backend-builder | F1 | Validación de entrada en un único lugar | RNF-Q-04 exige no duplicar reglas entre HTTP y dominio | Los esquemas Pydantic de entrada aceptan cualquier JSON interpretable (tipos `Any`, `extra="allow"`) y ceden la validación íntegra al dominio (formato de id, tipo, nombre, descripción, campos desconocidos, reflexiva, duplicados, inexistentes) | Cada regla se evalúa una sola vez; los errores HTTP y de ruta reutilizan las mismas funciones del dominio | Prueba de humo: `id` numérico → ERR-04, lista en `tipo` → ERR-04, campo `peso` → ERR-06, cuerpo no JSON → ERR-03 |
| 2026-10-03 | backend-builder | F1 | Sobre de error único y traducción HTTP | RNF-F1-08 y contrato de errores | Excepciones de dominio con `codigo` estable y detalles por campo; manejadores en `app/api/errores_http.py` traducen a HTTP y construyen `{"error": {codigo, mensaje, detalles}}`; rutas inexistentes → 404 `TIPO_NO_ENCONTRADO`; `Content-Type` distinto de JSON → 400 `PETICION_MAL_FORMADA` | Errores explícitos y nunca convertidos en resultados vacíos (RF-F1-12) | Prueba de humo de cada código ERR-01 a ERR-09 contra TestClient |
| 2026-10-03 | backend-builder | F1 | Persistencia y datos de demostración | AMB-F1-02: el brief no exige persistencia; el contrato exige poder inicializar con datos sintéticos | Repositorio en memoria detrás del puerto `RepositorioCatalogo`; conjunto sintético de demostración registrado por el mismo camino de validación que la API en `datos_demostracion.py`; `crear_aplicacion(catalogo)` permite arrancar vacío o con datos | No inventa regla de negocio; cambio de persistencia no afecta al dominio ni a la API | La app arranca con 6 elementos y 6 dependencias consistentes con `acceptance-criteria.md` §1; TestClient con catálogo vacío devuelve colecciones vacías |
| 2026-10-03 | backend-builder | F1 | Frontera snake_case/lowerCamelCase | Los modelos Python deben conservar `snake_case` y el JSON usar `lowerCamelCase` (§3.1 de `architecture.md`) | Esquemas Pydantic con `alias_generator=to_camel` y serialización por alias en FastAPI; la traducción ocurre solo en la capa `api` | El dominio expone `tipo_relacion`, `total_elementos`, etc.; el JSON viaja como `tipoRelacion`, `totalElementos` | Verificado en respuestas: `tipoRelacion`, `resumen.totalElementos`, `resumen.totalDependencias` presentes |
| 2026-10-23 | backend-builder | F2 | Algoritmo de impacto en el dominio | F2 requiere consultar elementos afectados (alcanzables hacia adelante) sin NetworkX | Método `Catalogo.obtener_impacto(id)` implementa recorrido en profundidad iterativo con pila y conjunto `visitados`; usa `_adyacencia_salida`; devuelve `Elemento` ordenados por `id` ascendente | El dominio ya tiene la adyacencia de salida; el recorrido propio evita NetworkX (RNF-F2-01, AC-F2-06); maneja ciclos y no duplica alcanzables | 23 tests de `test_impacto.py` pasan: AC-F2-01 a AC-F2-15, casos límite (inexistente, mal formado, vacío, sin aristas, cadena, múltiples caminos, ciclo) |
| 2026-10-23 | backend-builder | F2 | Caso de uso `ConsultarImpacto` | Orquestar validación de formato (ERR-05) y delegar en dominio (ERR-02 si inexistente) | Clase en `app/aplicacion/casos_de_uso.py` usa `validar_identificador_consulta` y llama `catalogo.obtener_elemento` + `catalogo.obtener_impacto`; devuelve tupla `(elemento, afectados)` | Separación de responsabilidades: HTTP no conoce el recorrido; dominio no conoce HTTP (RNF-Q-01, RNF-Q-02) | Tests verifican 404 ERR-02 para inexistente, 422 ERR-05 para mal formado, 200 con estructura correcta |
| 2026-10-23 | backend-builder | F2 | Endpoint `GET /api/v1/impacto/{id}` y esquemas | Contrato de `api-contract.md` §8: respuesta con `elemento`, `afectados[]`, `total` | `ImpactoRespuesta` con `ElementoImpactoRespuesta` (id, tipo, nombre); ruta en `app/api/rutas.py` llama a `ConsultarImpacto`; traduce errores de dominio a HTTP vía manejadores existentes | Reutiliza `ERR-02` y `ERR-05` del catálogo F1 (no códigos nuevos); respuesta determinista ordenada por `id` (RN-F2-11) | Tests: 200 con afectados, 200 total=0 sin aristas salientes, 404 inexistente, 422 mal formado, ciclo termina, catálogo vacío → 404 |
| 2026-10-23 | backend-builder | F2 | Diferenciación explícita de casos | RN-F2-03, RN-F2-04, RN-F2-09, RN-F2-10: inexistente ≠ sin afectados ≠ mal formado ≠ catálogo vacío | - Mal formado (patrón inválido) → 422 `IDENTIFICADOR_INVALIDO` (ERR-05)
- Inexistente (formato válido, no en catálogo) → 404 `ELEMENTO_NO_ENCONTRADO` (ERR-02)
- Existente sin aristas salientes → 200 `afectados: [], total: 0`
- Catálogo vacío → 404 `ELEMENTO_NO_ENCONTRADO` (nunca 200 []) | El cliente debe distinguir situaciones; error nunca se presenta como resultado válido (RF-F2-02, RF-F2-06) | Tests `test_ac_f2_03`, `test_ac_f2_04`, `test_ac_f2_11`, `test_ac_f2_12` verifican cada caso con códigos y cuerpos correctos |
| 2026-10-23 | backend-builder | F2 | Sin información de ciclos ni orden en respuesta | RN-F2-12, RF-F2-08: F2 no anticipa F3 | Respuesta `ImpactoRespuesta` solo tiene `elemento`, `afectados`, `total`; sin campos `ciclos`, `orden`, `nivel`, `tieneCiclo`; el recorrido maneja ciclos internamente sin exponerlos | Alcance por feature: F3 detecta y reporta ciclos; F2 solo calcula impacto | Test `test_ac_f2_14` confirma claves prohibidas ausentes en respuesta y en cada afectado |
| 2026-10-25 | backend-builder | Ajustes | Inventario en el modelo `Elemento` y cálculo de alerta en dominio | El requerimiento pide stock disponible, mínimo aceptable y alerta por debajo del mínimo, sin duplicar la regla en el frontend | `Elemento` incorpora `stock_disponible` y `stock_minimo` (solo `INSUMO`, enteros no negativos, 0 por defecto) y propiedades `estado_stock`/`alerta_stock`. `normalizar_inventario` rechaza stock en tipos que no son suministro y cantidades inválidas. La respuesta HTTP expone `stockDisponible`, `stockMinimo`, `estadoStock` y `alertaStock` | La regla vive en el dominio y viaja calculada a la interfaz; el frontend no decide cuándo hay alerta | `test_gestion_inventario_y_relaciones.py` (alta, valores por defecto, rechazo en no suministros, cantidades inválidas y recálculo al editar); suite completa en verde |
| 2026-10-25 | backend-builder | Ajustes | Reglas de dependencia y asociación del suministro en `Catalogo` | El requerimiento exige impedir relaciones entre tipos no permitidos y entre un suministro no asociado y un proceso o producto | Se añade `reglas_dependencia.py` con la matriz permitida y los motivos; `Catalogo.registrar_dependencia` y `actualizar_dependencia` validan tipos y, para un suministro que se enlaza a proceso o producto, exigen una arista entrante de proveedor o proceso. Se publica `GET /api/v1/reglas-dependencia` con las 16 combinaciones para que la interfaz las muestre antes de crear | Mantener la política en dominio garantiza consistencia entre mapa, formularios y API; exponerla evita que el frontend duplique la regla | `test_gestion_inventario_y_relaciones.py`; pruebas de reglas y endpoint; frontend consume la matriz y deshabilita combinaciones no permitidas |
| 2026-10-25 | backend-builder | Ajustes | Edición, borrado y cascada de relaciones | El requerimiento pide editar/eliminar elementos y relaciones sin dejar el grafo inconsistente | Endpoints `PUT/DELETE /elementos/{id}` y `PUT/DELETE /dependencias/{origen}/{destino}`. La edición de elemento conserva id y tipo. El borrado de elemento elimina sus aristas entrantes y salientes en la misma operación. El borrado de una relación inexistente responde `404 DEPENDENCIA_NO_ENCONTRADA`. Los cambios son atómicos: si la nueva relación no cumple las reglas, la original permanece | La cascada evita referencias colgantes; la inmutabilidad de id/tipo preserva el significado de las reglas y la trazabilidad; los códigos de error permiten distinguir inexistente de inválido | `test_gestion_inventario_y_relaciones.py`; pruebas HTTP de actualización y borrado; verificación de interfaz |
| 2026-10-25 | backend-builder | Ajustes | Impacto enriquecido con stock | El análisis de impacto debe considerar los suministros y presentar su stock | `ElementoImpactoRespuesta` incluye descripción y campos de inventario; `ImpactoRespuesta` añade `resumenStock` con total de suministros involucrados y cuántos están bajo el mínimo. El conjunto de afectados y el recorrido no cambian | El stock es información de contexto del impacto, no una regla de alcanzabilidad; enriquecer la respuesta evita consultas adicionales y permite actualizar el informe | `test_gestion_inventario_y_relaciones.py::test_impacto_incluye_estado_de_stock_de_los_suministros`; respuesta verificada por HTTP |
| 2026-10-25 | backend-builder | Ajustes | Ampliación del conjunto sintético de demostración | La demo solo cubría la línea de acero y el cliente pidió algunos elementos más de proveedor, suministro, proceso y producto coherentes con la empresa | Se añade la línea de madera: `PROV-MADERA`, `INS-TABLERO`, `INS-BARNIZ`, `PROC-ENSAMBLE` y `PROD-ESCRITORIO`, con cinco relaciones válidas. `INS-BARNIZ` queda por debajo de su mínimo para mostrar una segunda alerta de stock. La línea es independiente de la de acero, por lo que los impactos de `PROV-ACERO` e `INS-TORNILLO` no cambian | Una segunda línea de producto demuestra el catálogo sin alterar los casos de impacto ya verificados y mantiene todas las reglas de tipo y asociación | `pytest` completo en verde; `GET /api/v1/grafo` devuelve 11 elementos y 11 dependencias; scripts de aceptación F1 actualizados |
