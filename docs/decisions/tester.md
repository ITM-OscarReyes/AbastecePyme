# Decisiones — tester

Registro de decisiones de estrategia de verificación y criterios de prueba. Estructura y reglas comunes en `docs/decisions/decisions.md`.

| Fecha | Agente | Feature | Decisión o pieza | Problema o necesidad | Decisión adoptada | Motivo | Cómo se verificó |

| 2026-10-05 | `tester` | F1 | Entorno de pruebas del backend | El proyecto no tenía suite de pruebas ni dependencias de prueba instaladas | Entorno virtual en `backend/.venv` con FastAPI, Uvicorn, Pydantic, `pytest` y `httpx`; `pytest.ini` configura la-discovery de `backend/tests` | No se puede declarar PASS/FAIL sin ejecutar; instalar solo en el entorno virtual mantiene `requirements.txt` intacto, porque RNF-F1-01 lo define como dependencias de ejecución | `backend/.venv/Scripts/python.exe -m pytest` → 117 pruebas, todas en verde |
| 2026-10-05 | `tester` | F1 | Verificación del contrato HTTP sin dobles | AC-F1-01 a AC-F1-20 describen respuestas HTTP exactas; un doble de red no las verificaría | Suite pytest con `TestClient` para el grueso de casos, más `tests/verificacion_http.py` que habla con un servidor `uvicorn` real por `urllib` | `TestClient` es rápido para la mayoría de casos, pero `verificacion_http.py` confirma el contrato en el mismo proceso que sirve al frontend (C-02) | Ambos ejecutados: 117 pruebas pytest en verde y 20 comprobaciones HTTP reales, 20 PASS |
| 2026-10-05 | `tester` | F1 | Verificación de la interfaz mínima | AC-F1-14 exige comprobar la interfaz, no solo la API; el proyecto no tenía runner de frontend | `vitest` para el cliente de API contra el backend real y `playwright` con Chromium para la interfaz en navegador real | Cytoscape necesita `canvas`, que `jsdom` no implementa, así que el render de `GraphCanvas` es imposible fuera de un navegador; separar ambas suites evita simular el lienzo con dobles | `npm run test` (22 pruebas) y `npm run test:e2e` (11 pruebas) ejecutados contra Vite + Uvicorn reales |
| 2026-10-05 | `tester` | F1 | Servidor con catálogo vacío para AC-F1-13 y AC-F1-14d | La aplicación real carga datos de demostración, así que el estado vacío no era observable por HTTP | `backend/tests/servidor_vacio.py` expone la misma aplicación construida sobre un `Catalogo()` vacío; `playwright.vacio.config.ts` levanta ese backend y un Vite que proxya hacia él | Verificar el estado vacío contra un servidor real conserva la evidencia; calcularlo en el cliente falsearía el resultado | `npm run test:e2e:vacio` → 5 pruebas en verde con totales en cero y cero filas |
| 2026-10-05 | `tester` | F1 | Criterios de arquitectura como pruebas ejecutables | AC-F1-21, AC-F1-22 y AC-F1-23 piden una revisión, no una aserción observable en pantalla; redactarlos a mano no deja evidencia repetible | Análisis estático con `ast` en Python y recorrido del árbol de archivos en TypeScript | Un criterio de revisión debe poder fallar de forma reproducible cuando alguien introduce una regresión | `backend/tests/test_no_funcional_y_arquitectura.py` (arquitectura backend) y `frontend/src/test/arquitectura.test.ts` (frontend) |
| 2026-10-05 | `tester` | F1 | Alcance de la revisión estática del frontend | Las reglas de F1 viven en `app/dominio/validacion.py`; el criterio exige que no estén duplicadas en el frontend | Las pruebas buscan en los componentes el patrón `^[A-Z0-9]`, la comparación de longitud del `nombre`, la comparación `origen === destino` y el vocabulario de las reglas | Esas son las formas concretas en que una regla de F1 puede reaparecer en la interfaz; buscarlas por patrón detecta la regresión sin depender de una lectura manual | `frontend/src/test/arquitectura.test.ts` → 4 pruebas en rojo, todas las de AC-F1-22 |
| 2026-10-25 | `tester` | F2 | Suite de pruebas de impacto en backend | AC-F2-01 a AC-F2-15 y casos límite requerían verificación ejecutable exhaustiva | `test_impacto.py` expandido a 34 pruebas: recorrido en dominio sin NetworkX, alcanzables directos/indirectos, unicidad ante múltiples caminos, ciclo sin bucle infinito ni autoreferencia en afectados, elemento aislado, componentes conexas disjuntas, rendimiento lineal en 200 nodos/500 dependencias (<50ms), normalización de ID, errores 404/422 y ausencia de campos F3 | Garantiza cobertura total de criterios funcionales, no funcionales y casos límite en pytest | `pytest backend/tests/test_impacto.py` → 34 passed (0.55s) |
| 2026-10-25 | `tester` | F2 | Script de verificación HTTP de extremo a extremo sin dobles | AC-F2-01 a AC-F2-15 exigen comprobar el contrato REST sobre el servidor Uvicorn real consumido por el cliente | `backend/tests/verificacion_http_f2.py` ejecuta 16 escenarios con urllib contra `http://127.0.0.1:8000` (casos nominales, ciclo real, elemento terminal total 0, 404 ERR-02 sin datos de negocio, 422 ERR-05 id mal formado, determinismo, verificación de README) | Comprueba el comportamiento observable idéntico al que recibe el frontend en producción | `python tests/verificacion_http_f2.py` → 16 PASÓ, 0 FALLÓ |
| 2026-10-25 | `tester` | F2 | Verificación estática de arquitectura en frontend (AC-F2-06b, AC-F2-09) | Prohibición de calcular alcanzables o usar bibliotecas de grafos para impacto en el cliente | Tests automatizados en backend (`test_ac_f2_06b`) y en Vitest (`arquitectura.test.ts`) inspeccionan el código fuente de `frontend/src` verificando que no existan algoritmos de recorrido ni NetworkX/graphlib | Evita regresiones donde el frontend recalcule el impacto o duplique lógica del dominio | 14 pruebas de arquitectura en Vitest y `test_ac_f2_06b` en pytest en verde |
| 2026-10-25 | `tester` | F2 | Pruebas E2E de simulación de impacto en navegador real (Playwright) | AC-F2-01, AC-F2-01b, AC-F2-03, AC-F2-04, AC-F2-14 en la interfaz gráfica | `frontend/e2e/f2.spec.ts` con Chromium contra Vite (3000) y FastAPI (8000) reales: navegación al simulador, selección de componentes, visualización de severidad y afectados, mensaje de error 404 y verificación de ausencia de indicadores de ciclos/orden de producción | Valida la integración real UI-API-Backend sin dobles | `npx playwright test e2e/f2.spec.ts` → 5 passed (4.3s) |
| 2026-11-07 | `tester` | F3 | Suite QA independiente de orden de producción y ciclos | AC-F3-01 a AC-F3-11 y los casos límite de ciclos requerían verificación ejecutable propia, separada de la suite del implementador | `backend/tests/test_orden_produccion_f3_qa.py` con 19 pruebas: DAG, determinismo, ciclos directos/indirectos/múltiples/compartidos, vacío, aislados, un solo elemento, integración F1/F2, sin NetworkX, rendimiento y determinismo byte a byte | Permite auditar la implementación contra la API real montada con `crear_aplicacion` sin depender de los tests del backend-builder | `python -m pytest tests/test_orden_produccion_f3_qa.py -v` → 19 passed (0.68s) |
