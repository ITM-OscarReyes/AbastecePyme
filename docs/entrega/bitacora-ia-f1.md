# Bitácora de IA — F1 · Catálogo de dependencias

Uso de IA declarado para la Feature 1. El texto literal de cada
prompt quedó registrado en [`prompts/prompts.md`](../../prompts/prompts.md); el detalle y el motivo de
cada decisión están en [`docs/decisions/`](../decisions).

| Decisión o pieza | Herramienta/objetivo de IA | Propuesta recibida | Acepté o rechacé y por qué | Cómo la verifiqué |
|---|---|---|---|---|
| Reglas de calidad del código de los agentes | Definir qué agentes deben aplicar Clean Code, SOLID y Clean Architecture | Añadir los principios a todos los agentes del proyecto | Acepté parcialmente: solo a los agentes que escriben código (`backend-builder`, `frontend-builder`, `tester`) y con las reglas de nomenclatura según lenguaje. Rechacé aplicarlas a `orchestrator` y `auditor`, que no escriben código, para no imponer restricciones que no pueden cumplirse | Lectura de `.opencode/agent/*.md` y de `AGENTS.md` tras el cambio, y ejecución de `npm run lint` y `pytest` sin errores |
| Especificación técnica de F1 | Generar con `analyst` requisitos, modelo del grafo, contrato de API y criterios de aceptación | Documentación completa de F1 en Markdown, sin escribir código | Acepté con dos límites: solo F1 (nada de F2, F3 ni F4) y cero archivos de código, para que la especificación no invadiera la implementación ni el alcance. Ante ambigüedad debía documentarse como decisión pendiente en lugar de inventar una regla | Revisión de que `docs/requirements.md`, `graph-model.md`, `api-contract.md`, `architecture.md` y `acceptance-criteria.md` no especifiquen F2/F3/F4, y de que no exista ningún archivo `.py` o `.ts` generado por esa ejecución |
| Dirección de las aristas y representación del grafo | Definir hacia dónde apunta cada flecha y cómo se guarda el grafo | Arista dirigida `origen → destino` con `tipoRelacion: "habilita"`, grafo propio sin librerías externas | Acepté la dirección única `requisito previo → dependiente` porque da una sola lectura para todos los tipos de elemento y la frase "Para producir ___ necesito ___" se invierte de forma verificable. Rechacé la alternativa de usar una dirección por tipo de elemento: el brief prohíbe arreglar una dirección confusa con condicionales | `GET /api/v1/grafo` devuelve la misma dirección que declara `docs/graph-model.md`, y el e2e `AC-F1-14c cada flecha va de origen a destino` comprueba en navegador que cada flecha va de `origen` a `destino` |
| Uso de NetworkX | Añadir NetworkX para construir el grafo y detectar ciclos | Instalar `networkx` en `requirements.txt` y usarlo en el dominio | Rechazé: la regla no negociable de `AGENTS.md` solo permite NetworkX para visualizar resultados ya calculados. Usarlo para construir el grafo o consultar adyacencia rompería `AC-F1-15` | `backend/requirements.txt` contiene solo `fastapi`, `uvicorn` y `pydantic`; búsqueda de `networkx` en `backend/app/` sin coincidencias; `test_no_funcional_y_arquitectura.py` lo comprueba de forma reproducible |
| Backend de F1 | Implementar con `backend-builder` la API REST y el dominio | FastAPI con casos de uso, puertos, repositorio en memoria y datos de demostración | Acepté la separación en `dominio` / `aplicacion` / `infraestructura` / `api`: mantiene las dependencias apuntando hacia dentro y permite verificar que el dominio no importa el framework HTTP. Rechacé cualquier atajo que pusiera las validaciones en las rutas, porque duplicaría las reglas del catálogo | `pytest` → 117 pruebas en verde; `python -c "import app.main"` sin errores; revisión de que `dominio/` no importa `fastapi` ni el repositorio; `AC-F1-21` como prueba ejecutable |
| Interfaz de F1 | Construir con `frontend-builder` la interfaz que consume la API | React + Cytoscape dibujando la red y los modales de alta | Acepté Cytoscape solo como dibujo de lo que devuelve la API, con la condición de que no calcule nada. Rechacé que el cliente de API o los componentes validaran el catálogo: `docs/architecture.md` prohíbe una segunda versión de las reglas | `npm run lint` y `npm run build` sin errores; `arquitectura.test.ts` comprueba por patrón que ningún componente contenga las reglas de F1 |
| Alcance del frontend | Revisar lo que había implementado el frontend | Se detectaron `calcularImpacto`, `calcularOrdenYDetectarCiclos`, paneles de impacto y producción, y un veredicto de ciclos en el cliente | Rechacé por completo: F2, F3 y F4 están fuera de alcance y el backend no expone esos datos, así que calcularlos en el cliente habría producido resultados no verificables y una segunda versión de los algoritmos. Se eliminó todo y el cliente quedó con los 6 endpoints de F1 | Búsqueda de `impacto`, `ciclo`, `topol`, `ordenTrabajo` y `dashboard` en `frontend/src` sin coincidencias; `npm run test` y `npm run test:e2e` en verde |
| Reglas de validación duplicadas en los modales de alta | Verificación de `tester` sobre `AC-F1-22` | 4 pruebas en rojo: los modales reproducían la regex del `id`, la longitud del `nombre` y la comprobación `origen === destino` | Acepté el hallazgo y la corrección propuesta: los modales dejan de decidir si el dato es válido y muestran el error que devuelve la API. No toqué la validación del backend, que es la única fuente | `npm run test` → 22 pruebas en verde (las 4 de `AC-F1-22` incluidas), `npm run test:e2e` → 11 y `npm run test:e2e:vacio` → 5; búsqueda de esos patrones en `frontend/src/components/` sin coincidencias |
| Ejecución de la auditoría de cierre de F1 | Invocar al subagente `auditor` para cerrar el pipeline | Ejecutar la auditoría con el agente especializado | Rechacé quedarme sin auditoría: la invocación falló dos veces con `Subagent failed ... Error from provider (Console): OpenCode's free tier can only be used from within OpenCode`. Se completó el tramo manualmente bajo las mismas reglas, dejando constancia de que no lo hizo un agente | Decisiones registradas en `docs/decisions/orchestrator.md` y `docs/decisions/auditor.md`, y re-ejecución de las seis suites de prueba |
| Formato del script de aceptación | Ajustar `backend/tests/verificacion_http.py` | El script existente imprimía `PASS`/`FAIL` y el detalle solo en fallo | Rechacé ese formato: el script debe imprimir qué se esperaba y qué se obtuvo en todos los escenarios, y cubrir además consulta sin datos, origen o destino inexistente y ciclo | `python tests/verificacion_http.py` → 28 escenarios, 28 PASÓ, con `esperado` y `obtenido` en cada uno y código de salida `1` si algo falla |
